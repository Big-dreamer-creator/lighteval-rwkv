# Adding a Custom Task

Lighteval provides a flexible framework for creating custom evaluation tasks. This guide explains how to create and integrate new tasks into the evaluation system.

## Step-by-Step Creation of a Task

> [!WARNING]
> To contribute your task to the Lighteval repository, you would first need
> to install the required dev dependencies by running `pip install -e .[dev]`
> and then run `pre-commit install` to install the pre-commit hooks.

### Step 1: Create the Task File

First, create a Python file or directory under the `src/lighteval/tasks/tasks` directory.
A directory is helpfull if you need to split your file into multiple ones, just make sure to have one of the file named `main.py`.

### Step 2: Define the Prompt Function

You need to define a prompt function that will convert a line from your
dataset to a document to be used for evaluation.

```python
from lighteval.tasks.requests import Doc

# Define as many as you need for your different tasks
def prompt_fn(line: dict, task_name: str):
    """Defines how to go from a dataset line to a doc object.
    Follow examples in src/lighteval/tasks/default_prompts.py, or get more info
    about what this function should do in the README.
    """
    return Doc(
        task_name=task_name,
        query=line["question"],
        choices=[f" {c}" for c in line["choices"]],
        gold_index=line["gold"],
    )
```

### Step 3: Choose or Create Metrics

You can either use an existing metric (defined in [`lighteval.metrics.metrics.Metrics`]) or [create a custom one](adding-a-new-metric).

#### Using Existing Metrics

```python
from lighteval.metrics import Metrics

# Use an existing metric
metric = Metrics.ACCURACY
```

#### Creating Custom Metrics

```python
from lighteval.metrics.utils.metric_utils import SampleLevelMetric
import numpy as np

custom_metric = SampleLevelMetric(
    metric_name="my_custom_metric_name",
    higher_is_better=True,
    category="accuracy",
    sample_level_fn=lambda x: x,  # How to compute score for one sample
    corpus_level_fn=np.mean,  # How to aggregate the sample metrics
)
```

### Step 4: Define Your Task

You can define a task with or without subsets using [`~tasks.lighteval_task.LightevalTaskConfig`].

#### Simple Task (No Subsets)

```python
from lighteval.tasks.lighteval_task import LightevalTaskConfig

# This is how you create a simple task (like HellaSwag) which has one single subset
# attached to it, and one evaluation possible.
task = LightevalTaskConfig(
    name="myothertask",
    prompt_function=prompt_fn,  # Must be defined in the file or imported
    hf_repo="your_dataset_repo_on_hf",
    hf_subset="default",
    hf_avail_splits=["train", "test"],
    evaluation_splits=["test"],
    few_shots_split="train",
    few_shots_select="random_sampling_from_train",
    metrics=[metric],  # Select your metric in Metrics
    generation_size=256,
    stop_sequence=["\n", "Question:"],
)
```

#### Task with Multiple Subsets

If you want to create a task with multiple subsets, add them to the
`SAMPLE_SUBSETS` list and create a task for each subset.

```python
SAMPLE_SUBSETS = ["subset1", "subset2", "subset3"]  # List of all the subsets to use for this eval

class CustomSubsetTask(LightevalTaskConfig):
    def __init__(
        self,
        name,
        hf_subset,
    ):
        super().__init__(
            name=name,
            hf_subset=hf_subset,
            prompt_function=prompt_fn,  # Must be defined in the file or imported
            hf_repo="your_dataset_name",
            metrics=[custom_metric],  # Select your metric in Metrics or use your custom_metric
            hf_avail_splits=["train", "test"],
            evaluation_splits=["test"],
            few_shots_split="train",
            few_shots_select="random_sampling_from_train",
            generation_size=256,
            stop_sequence=["\n", "Question:"],
        )

SUBSET_TASKS = [CustomSubsetTask(name=f"task:{subset}", hf_subset=subset) for subset in SAMPLE_SUBSETS]
```

### Step 5: Add Tasks to the Table

Then you need to add your task to the `TASKS_TABLE` list.

```python
# STORE YOUR EVALS

# Tasks with subsets:
TASKS_TABLE = SUBSET_TASKS

# Tasks without subsets:
# TASKS_TABLE = [task]
```

### Step 6: Creating a requirement file

If your task has requirements, you need to create a `requirement.txt` file with
only the required dependencies so that anyone can run your task.

## Running Your Custom Task

Once your file is created, you can run the evaluation with the following command:

```bash
lighteval accelerate \
    "model_name=HuggingFaceH4/zephyr-7b-beta" \
    {task} \
    --custom-tasks {path_to_your_custom_task_file}
```

### Example Usage

```bash
# Run a custom task with 3 shot evaluation
lighteval accelerate \
    "model_name=openai-community/gpt2" \
    "myothertask|3" \
    --custom-tasks community_tasks/my_custom_task.py
```

## Mandatory RWKV Benchmark Audit

This section applies to the RWKV producer, including changes to existing
benchmarks. It does not change the evaluation protocol for other LightEval
models. Read it before editing task prompts, metrics, extraction, or publication.

### 1. Record the benchmark contract before implementation

Record the native benchmark reference and the existing LightEval prototype;
selector and expanded subtasks; dataset revision, subset, split and sample/gold
fields; `Doc.query`, `choices` and `gold_index`; few-shot behavior; metric name,
aggregation and sample count; solver/scorer; NoCoT/FakeCoT/CoT decision; actual
`SamplingMethod` and endpoint; template, stop/EOS behavior, context and effective
token budget; output format, extraction failure and truncation definitions.
A label or `generation_size` is not evidence of request routing.
Obtain explicit user approval before any score-affecting change, including a
bug fix, scoring-rule removal or cleanup that changes results. An explicit
request for the specific change is approval; otherwise ask before editing.

### 2. Keep RWKV policy private

Follow `Registry._update_task_configs` and `Pipeline` as implementation
prototypes. RWKV-only changes belong to `RWKVRegistry`/`RWKVPipeline` in
`src/rwkv_eval/main.py`, using the registry's deep-copied configurations.
Do not mutate `TASKS_TABLE`, metric singletons, native prompt functions, or
process-wide registries. Shared optional response fields must have neutral
defaults and survive indexing, caching and serialization. Demonstrate that a
native task loaded before and after RWKV evaluation has unchanged behavior.

### 3. Verify executable request behavior

- NoCoT multiple-choice uses `LOGPROBS` and `/v1/completions`, with native
  `multiple_choice(cache=True)`/`choice()` wiring where applicable. Multiple-token
  candidates use the sum of conditional token logprobs, not perplexity.
- Check the exact prefix and each candidate sent by the adapter. The selected
  candidate input displayed in details must be a retained request string, not
  choices reconstructed by the publisher. Continuation tasks such as ARC and
  Winogrande do not send all alternatives in one prompt.
- Generation uses `GENERATIVE` and `/v1/chat/completions`, with captured
  server-rendered text. No rendered prompt means no publication. Reasoning must
  not inherit an answer-only newline stop. Send the configured generated-token
  budget unchanged; the backend's total context is configured independently.
- Verify these facts in actual logs, including when resuming from cached output.

### 4. Audit the answer lifecycle and grading

Keep raw server output separate from metric input and concise uploaded answer.
Use `answer_extractor_for_benchmark` and `extract_answer` in
`src/rwkv_eval/answer_extract/free_response.py` for the same extraction contract.
Math prefers balanced boxed expressions; choices yield a valid letter; code
uses the final fenced program. Determine whether thinking is still open from
the captured rendered prompt: a Fake Think wrapper may already close there,
whereas an Open Think wrapper must close in the response. Fake Think may also
split its closing tag across the actual boundary (`</think` in the prompt and
`>` at the start of generation). Parse this captured boundary without changing
either published string. An unterminated wrapper or extraction failure must
not fall back to the reasoning trace.
Keep extraction failure as `None` internally for grading, and serialize its
uploaded answer as `"-"`. Preserve the raw assistant output, failure bucket and
`is_passed=false`; never grade the display placeholder as an extracted answer.
Validate dataset gold extraction before evaluation.

Use the same individual comparator for native metrics and details. Preserve
native `maj@n`, `pass@k` and `avg@n` aggregation, but never assign the aggregate
score to every rollout. Compare concise math values with exact agreement first
and the native mathematical-equivalence comparator next. Multiple accepted
answers remain distinct alternatives; benchmark multi-part targets are not
alternatives. For ASDiv, apply native unit removal to every semicolon-separated
target and compare all parts in order. Named model values may be ordered only
from the captured question, never selected using gold values. Preserve its
textual targets with exact matching rather than interpreting names as algebra.
For OlympiadBench, `is_multiple_answer` requires the whole comma-connected
answer, not any single component. Ordinary extraction failure is not an
output-limit truncation. Both live and parquet publication use `get_detail` in
`src/rwkv_eval/upload.py`; no independent replay registry or grader is allowed.

### Correction contracts: TruthfulQA, MATH and MATH-500

- `truthfulqa:mc`: native prototype `truthful_qa_multiple_choice_prompt` and
  `TruthfulqaMCMetrics.compute/mc1`; dataset `truthfulqa/truthful_qa`, subset
  `multiple_choice`, split `validation`. `mc1_targets` and `mc2_targets` remain
  separate groups within `Doc.choices`, with `specific.len_mc1` marking their
  boundary. Keep both native metrics; the published first metric is MC1, so
  its detail selects only MC1 candidates, displays the MC1 gold letter and
  grades that choice. NoCoT remains `LOGPROBS` through `/v1/completions`, native
  `multiple_choice(cache=True)`/`choice()`, with the retained selected request.
  Do not display a merged MC1/MC2 distribution as the answer or use MC2's
  probability as a Boolean pass flag. Native NumPy scalar metrics must remain
  numeric when converting to publication values.
- `math` expands to the native subject tasks; `math_500` is a single selector.
  Prototypes are the native task formatters, `extract_math_answer` and
  `MultilingualExtractiveMatchMetric`. Keep the native query, subject split,
  sampled row IDs, complete gold and aggregation (including MATH's multiple
  rollouts). CoT remains `GENERATIVE` through `/v1/chat/completions`, captured
  `bot` prompts, no answer-only stop and a generated-token budget up to
  24576, independent of prompt length. A closed response's concise expression may use `cot x` or LaTeX
  `\\cot x`; normalize recognized function notation for extraction and
  comparison. In prose fallback, preserve thousands-separated numerals and
  exclude trailing `because`/`since` explanations rather than extracting
  their last number. Preserve commas in intervals and multi-part expressions.
  Failed extraction stays `None` internally and `"-"` in details; an unclosed
  thinking trace remains failed even if it mentions the correct answer.

### Approved RWKV expected-score restoration

The user explicitly approved restoring the rule introduced in `59b3974f`.
Prototypes: `ExactMatches.compute_one_item`, `PassAtK.pass_at_k` and the original
RWKV missing-choice branches. `RWKVRegistry` installs private
`RWKVExactMatches(choice=True)` and `RWKVPassAtK` on generative choice metrics;
native metric singletons and non-RWKV registry copies remain unchanged.

Affected registered selectors are GPQA `diamond`/`main` (and `extended` when
selected): dataset `Idavidrein/gpqa`, matching native `gpqa_*` subset, `train`
split. Keep native `Question` and three `Incorrect Answer *`/`Correct Answer`
fields, shuffled displayed options, `Doc.query`, A–D `Doc.choices`, sampled row
IDs and `gold_index`. CoT remains actual `GENERATIVE` through
`/v1/chat/completions`, the captured `bot` template, no newline stop and a
24576-generated-token budget. NoCoT `LOGPROBS` scoring is unchanged.

An extracted correct letter scores 1, a wrong letter scores 0 and extraction
failure scores 0.25. This restores the fixed historical value, not a new
choice-count-dependent rule. For the historical pass@1 case with no score-1
rollout, `n == len(scores)` and `missing > 0`, return `1 - 0.75**missing`;
otherwise retain native aggregation. Main/extended retain their single-response
aggregation; math and short-answer failures remain unchanged.

Extraction failure remains `None` internally, empty only in native metric input,
and `"-"` in publication. Raw output and the captured prompt are retained;
failed or truncated details remain `is_passed=false` in the failure bucket.
Fractional expected credit contributes to the score without fabricating a
completed answer. Truncation accounting continues to use the actual finish
reason. Validate native/RWKV/native isolation, mixed correct/wrong/missing
rollouts and preserved failure details, then the required 1.5B/2.9B ten-question
samples before publishing replacement scores; preserve old rows and exact
request-budget evidence when regrading retained caches.

### RWKV budget and completion-cache contract

RWKV budgets such as 4096/8192/16384/24576 limit generated tokens, not total
prompt plus completion length. Send the configured `max_new_tokens` unchanged,
without subtracting prompt length or requiring an extra tokenization request.
The inference backend's separately configured context is sufficiently large;
manifest/weight context metadata is not a measured server context limit.
Prototype: native OpenAI completion `max_tokens` and `usage.prompt_tokens`.
Preserve the actual requested budget, server-reported prompt token count,
rendered prompt and child seeds in `ModelResponse`, native caching and indexing.

Prototype: `LiteLLMClient.__call_api_parallel`, `SampleCache`, and
`EvaluationTracker.append_streaming_completion`. RWKV alone dispatches `n=1`
HTTP rollouts, preserving native vLLM `ParentRequest` seed + child-index
semantics. Harvest in completion order, append/fsync the native cache journal,
then restore document/rollout order for metrics. Resume missing children from
that journal; recover only an interrupted final line. RWKV `LOGPROBS` requests
also append/fsync each completed document in completion order, preserving exact
candidate inputs and summed sequence logprobs; failed peers do not discard those
checkpoints, and resumption restores document order while requesting only missing
documents. Count NoCoT admission capacity in candidate completion sequences,
not documents: a document with many alternatives must not multiply the endpoint
pool capacity. Refill released capacity immediately in completion order; a
candidate batch larger than the configured pool occupies it alone. Native choice
requests, candidate token sums and output ordering are unchanged. Prototype:
the same RWKV completion journal and native `SampleCache`.
Other LiteLLM providers retain their native batch request and caching behavior.

RWKV model pools run in separate spawned processes, following the native dataset
process-worker prototype. Each pool owns its full benchmark queue, native random
state, grader and publication; neither serial models nor a cross-model benchmark
barrier may idle the other pools. Production uses one transient producer unit per
model so retries/resumption are independent. Measure running/waiting requests and
token-rate deltas for all four pools at `https://vllm.rwkvos.com/metrics?model=...`;
configured request limits alone do not establish inference saturation. Both RWKV
LOGPROBS and generation use an explicit 14400-second HTTP request timeout;
LOGPROBS retries transient TLS/connection/read failures and upstream 5xx at most
six times, following the native generation retry prototype. Retries preserve the
exact original request, candidate span and token budget, and never fabricate a
response. Prompt, metric, sampling count and generated-token budgets remain
benchmark-native.

Each producer detail records the actual requested generated-token budget.
Scoreboard's single score-level sampling config records their maximum (the
request ceiling); actual per-rollout budgets remain in saved producer
details/cache, with the base parent seed in the shared sampling config and
actual child seeds in the response. Legacy cached responses without request
budget evidence may be regraded for corrections, but must not be represented
as having newly verified budgets. Live acceptance checks the outgoing completion
limit, captured rendered prompt, returned usage and finish reason; never
reconstruct prompt evidence or invent request metadata.

### 5. Regression and publication gate

Before production publication, record results of:

- hermetic request/prompt, stop/budget, nested-box, mathematical-equivalence,
  invalid-choice, unclosed-think, failure-placeholder and multi-rollout tests;
- native/RWKV/native task-isolation tests and both streaming/non-streaming batch
  post-processing tests;
- live/parquet detail equality and candidate-input cache/serialization tests;
- interruption/resumption and streaming completed-output validation;
- ten-question samples on both 1.5B and 2.9B, uploaded to the test dashboard,
  with observed request types, modes, budgets and truncation rates;
- dashboard inspection of correct, wrong and failed outputs where present,
  separating model capability from extractor/grader faults. Do not require the
  model to manufacture a failure; use controlled fixtures for missing categories.

Acceptance requires actual scores and details in the test database for the
required model/benchmark pairs. Query the previously reported abnormal answer,
ground-truth, grading, prompt and mode patterns, and compare stored inputs with
retained request evidence. Record score IDs, detail counts and anomaly counts.
An empty result set, producer startup, or passing unit tests is not acceptance.

Document unfinished checks as blockers, not successful validation. Obtain user
confirmation before adding files. For corrections, preserve audit history and
expire only exact affected score IDs after fetching a fresh manifest; never
clear the database or rerun unrelated model/benchmark pairs. Do not change
inference or Scoreboard implementation from this repository.
